The bug was real. My first explanation wasn't.

A CAPTCHA bypass I reported held up. My first account of why it worked did not. Disproving my own explanation was the actual work.

Lucas Wesson · September 2026

Testing a web form under an authorized disclosure program, I found a CAPTCHA that did not stop automation. The finding was correct and it was accepted. The interesting part, and the reason I am writing it down, is that the first explanation I wrote for why it worked was wrong, and I only caught it because I went looking for a way to prove myself wrong.

This is a small bug. I am not using it to claim a scalp. I am using it because it is a clean example of the thing I think actually separates a useful security report from a noisy one, and it is the same discipline whether a human wrote the report or a model did.

The finding at first glance

The form protected itself with a five character image challenge, and the expected answer was recoverable from the page that served the form. From there the write-it-up reflex is immediate: the answer is in the source, so the check must be in the browser, so validation is client-side only and the CAPTCHA is trivially bypassable. That is what I wrote in the first draft. It reads well. A scanner would flag it the same way, and so would a model asked to triage the page.

It was also not quite true.

The test that changed the report

Before sending anything, I ran the check I try to run on every finding: assume my explanation is wrong and look for the one observation that would disprove it. If validation really happened only in the browser, a submission that never touched the browser should be accepted no matter what answer it carried. So I tested that assumption directly, with a deliberately wrong value.

The server rejected it.

One deliberately wrong answer, refused by the server, killed my first explanation. The server was validating.

So the browser-only story was false. Had I shipped the first draft, a triager could have poked one wrong value at it, watched it get rejected, and closed the whole thing as not reproducible. The finding would have been real and I would have lost it on a bad explanation.

What was actually wrong

The correct account is narrower and worse. The server did validate the answer, but the value it checked against was disclosed to the client in the same exchange that posed the challenge. The check was real; the secret it depended on was handed to the untrusted party in the same breath it was demanded back. I will leave the mechanics there, since the specific target is still in disclosure. The class is what matters.

That class is a recognized one, not a clever trick. MITRE catalogs it as CWE-602, Client-Side Enforcement of Server-Side Security: the enforcement decision relies on data the application itself surrenders to the client.[1] The point of a challenge like this is to be something an automated client cannot produce on its own; once the expected answer reaches that client, the only property that made it a control is gone.[2] The fix is equally boring: keep the answer on the server, send the client an image or an opaque reference, and compare on submission.

Why the correction is the whole job

Two reports could have come out of this. The first: client-side CAPTCHA, validated in the browser, trivially bypassable. Confident, wrong in its mechanism, and easy to disprove in one request. The second: the server validates, but against a value it discloses in the same response, so an automated client passes the check every time. Less dramatic, precise, and it survives the first person who tries to break it.

The distance between those two reports is not more scanning or more findings. It is one negative control I ran against my own claim before trusting it. That is the part I have come to think of as the real deliverable.

It matters more now, not less. When a report costs seconds to generate, the format is free and the confidence is free. A generated triage of that page would very plausibly have produced my first explanation: answer in source, check in browser, client-side, bypassable. Fluent, and wrong in the same way I was, for the same reason. The scarce skill is not producing the paragraph. It is being able to disprove your own paragraph, and knowing which observation would do it.

That is the same skill I use evaluating model output for a living: the answer that reads as correct is not the finished work. Checking whether it is actually correct is. A CAPTCHA that grades its own answer key is just a small, honest reminder of where the value is.
